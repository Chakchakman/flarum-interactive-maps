# v0.3 Alpha.1 — visible post-map token synchronization

Owner authorized moving to the next Roadmap stage on 2026-10-27 after discussing the GM checks. This first focused step adds automatic token snapshots to embedded post maps. It does not declare all v0.3 features complete or authorize release/merge. No migrations, external realtime service, paid dependencies or new production packages.

## Implemented contract

- One scheduler per forum tab polls visible/near-visible embedded maps about every five seconds. Up to 20 unique post IDs share a request; larger sets are processed in sequential chunks without overlapping cycles. Duplicate consumers share the request. Hidden tabs and offscreen boards do not schedule polls; removal unregisters the board. Returning to a visible tab wakes the scheduler.
- GET `/api/chak-map-sync?postIds=1,2` is authenticated, read-only and bounded. Every post is resolved through Flarum's actor-specific visibility and comment-post checks before map links/tokens are loaded. Missing, detached and inaccessible posts all return only `available:false`. Authorized snapshots carry mapId, token view data and current manage capability; no background/title/grid payload is repeatedly sent. Response caching is private/no-store.
- Snapshots update positions, creation/removal and owner presentation without replacing board zoom/pan or showing a loading flash. A changed association reloads that post's existing full-map endpoint. Geometry/background/title/grid edits still use the explicit refresh button. No token writes are generated by polling.
- A drag or pending write blocks refresh application. A local activity epoch also rejects reads begun before a completed drag/write, even when no write is pending by response time. Manual full-map reads have the same epoch guard.
- Temporary errors retain the last shown board, display a local retry notice and back off to 10/20/30 seconds; a successful snapshot restores the five-second interval. Authorization failure clears the board. No repeating global alert flood.

## Scope limits

The existing server still accepts last committed writes to a token. Distributed compare-and-swap/conflict rejection and presence are **not implemented** by this step. Do not describe local stale-read protection as a cross-client lock. WebSockets/SSE, differential token revisions and changes to the staff editor's existing refresh are outside this focused branch. Touch-pan/pinch remain deferred from Alpha.5. Third-party privacy package compatibility remains conditional on identifying/testing the actual package; core private flags and synthetic scopers verify the integration contract.

## Automated validation

Eight deterministic scheduler tests cover batching/deduplication, hidden/offscreen/removal cleanup, bounded concurrency, busy consumers, epochs across finished writes, independent post payloads, error backoff/recovery and malformed responses.

Three real-Flarum browser cases add: two-client movement and reassignment without refresh; authentication/input bounds/mixed authorized-missing IDs; hiding/restoring an embedded post; two boards sharing a batch; actual IntersectionObserver offscreen pause; controlled document-hidden signal and resume; delayed real snapshot across a successful pointer drag; and a simulated 503 that retains the board and automatically retries. The hidden-tab signal is controlled in headless Chromium and is not claimed as a physical-device/tab acceptance test. All write/auth checks and normal snapshots use the real server; only timing/error and visibility signal fixtures are controlled.

The installed-Flarum transaction test also verifies the batch endpoint under each hidden/private post/discussion state and under independent extension scopers, checking safe unavailable shapes and restoration. Synthetic fixtures roll back. Run only on the isolated named fixture forum; never run these fixture-creating suites against the owner's database.

The first browser run caught a real new-code bug: storing window timer functions as object methods caused Illegal invocation before initial map load. Default timer wrappers fix the receiver; all three targeted browser cases then passed. No assertions were removed to hide the failure. Final full-suite and exact CI results are recorded in PROJECT-CONTEXT.

## Owner acceptance after the exact tested build is installed

Use a disposable map/post and two browser profiles/accounts. Open the same embedded board for staff and a player owning a token. Move from either client and verify the other updates in approximately five seconds without pressing refresh or reloading. Verify reassignment removes the old owner's drag capability; other tokens remain read-only for that player. Keep two maps in a discussion and check independent zoom. Switch tabs/scroll away and return: the map refreshes without coordinate jump-back. Check normal thread scrolling and composer/BBCode still work. Do not move the original protected map/post link for testing. No migration is required; source builds must regenerate JS. This step remains pending owner acceptance and release approval.

Local final: 51/51 JS tests/build, 17/17 browser scenarios (3.3m), Composer/PHP syntax/access/grid/transaction/migration checks and installed-Flarum batch privacy assertions passed. No production DB migration. CI and owner acceptance remain separate statuses.
